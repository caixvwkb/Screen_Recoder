## 打包卡死修复：Nuitka × PyMuPDF 巨型 wrapper（PASS 1 卡住 / C1002）

现象：新增 PyMuPDF 依赖后，`python -m nuitka ... mainwindow.py` 长时间卡在
PASS 1 的 `pymupdf` / `pymupdf.mupdf`（98% 附近不动），继续往下会 C 编译
数小时并 `C1002: compiler is out of heap space`。

## 根因

PyMuPDF 有**两套实现**，`import fitz` 命中哪套由版本决定：

| PyMuPDF | 实现        | 说明                                                         |
| ------- | ----------- | ------------------------------------------------------------ |
| 1.22 系 | **classic** | 小型 `_fitz.pyd`（静态链接 MuPDF），无巨型 wrapper           |
| 1.23+   | rebased     | 新增 `mupdf.py`（约 5 万行 SWIG wrapper），Nuitka 会把它编译成**约 182 万行 C** |

本机原装 1.28.2 = rebased → Nuitka PASS 1 分析极慢（卡住）+ 编译 C1002。

## 解决方案（正解：锁定 classic 1.22，不是加 nofollow 参数）

1. **降级**：`pip install "pymupdf==1.22.*"`（当前 1.22.5）
2. **pyproject.toml**：依赖改 `"PyMuPDF>=1.22,<1.23"`；include_modules 只留 `"fitz"`（1.22 无 `pymupdf` 模块名）
3. **代码适配**：`folder_ocr.py` 兼容导入已覆盖（`import pymupdf` 失败自动回退 `import fitz`），
   但修复了一个隐藏 bug——原 except 分支在回退 fitz 成功后仍错误地打印"未安装"并 return，
   现在 fitz 回退成功会继续处理 PDF
4. API 兼容：`fitz.open` / `get_pixmap(dpi=150)` 在 1.22 classic 下正常（已实测）

## 陷阱提醒（不要用 --nofollow-import-to=pymupdf.mupdf）

有人为绕开 C1002 加 `--nofollow-import-to=pymupdf.mupdf`，编译是快过了，但
Nuitka 不会把 `_mupdf` C 扩展打进包 → **exe 能生成但一运行 `import fitz` 就崩**。
属于"构建成功但产物是坏的"。所以采用降级 classic 才是正道。

## 打包命令（建议 standalone 多文件，勿用 --onefile）

```bat
python -m nuitka --standalone --windows-console-mode=disable --enable-plugin=pyside6 --nofollow-import-to=torch --nofollow-import-to=sympy --output-dir=output mainwindow.py
```

- `--standalone`：多文件 dist 输出、启动快（符合本软件定位）。`--onefile` 要把
  onnxruntime + rapidocr 模型 + PyMuPDF 等大依赖全塞进单 exe，打包体积巨大且启动要
  解压几百 MB，非常慢。
- `--nofollow-import-to=torch/sympy`：onnxruntime 会间接 import torch/sympy，
  不排除会让 Nuitka 优化器崩溃（此前已修复过）。

- 文字层 PDF 提取、扫描件渲染 OCR、get_pixmap 渲染全部正常 ✅
- folder_ocr 回退逻辑修复后 PDF 路径工作正常 ✅
- 编译通过 ✅

## 踩坑：pyside6-deploy 不读 pyproject.toml 的 [tool.pyside6-deploy]（2026-09-07）

- 现象：pyproject.toml 配置了 icon/nuitka_args/drop_plugins，pyside6-deploy 全不生效，
  仍用内置默认参数 -> 跟进编译 torch._dynamo.pgo -> NuitkaOptimizationError 崩溃
- 根因：PySide6 的 tomllib 解析只用于 [tool.pyside6-project]（Qt Creator 项目文件列表）；
  pyside6-deploy 只认 INI 格式 --config-file 或内置默认，pyproject 的 deploy 段是摆设
- 结论：打包一律直跑 Nuitka（参数全在命令行可控）
- 可用命令：
  python -m nuitka --standalone --windows-console-mode=disable --enable-plugin=pyside6
    --nofollow-import-to=torch --nofollow-import-to=sympy
    --noinclude-qt-translations --windows-icon-from-ico=screen.ico
    --output-dir=output mainwindow_fluent.py


### 重新打包前必做：清 Nuitka 缓存

- Nuitka 增量构建会复用缓存；若源码模块改动后直接重打包，可能带上旧模块
  （实际踩坑：ocr.py 已改、exe 仍带旧探测逻辑，导致打包版 OCR 引擎禁用）。
- 重新打包前执行：python -m nuitka --clean-cache=all
  或直接删除 output 目录（*.build / *.dist）后重新构建，保证全量重编。


### Nuitka 打包环境判定坑（2026-09-08）

- Nuitka **不设置 sys.frozen**（那是 PyInstaller 的约定），编译标记是全局 `__compiled__`。
- 代码里判断"是否打包环境"必须双兼容：`getattr(sys, "frozen", False) or "__compiled__" in globals()`
- 否则打包版会把程序根算到 Nuitka 伪路径上，导致 exe 同级 models/ 外置模型探测失败
  （OCR/ASR 全部识别为空、md 只剩文件名）。项目已在 paths.is_compiled() 统一处理。

### rapidocr config.yaml 打包缺失 → OCR 引擎禁用（2026-09-08，已修）

- 现象：模型已拷 exe 同级，批量 OCR 仍只输出文件名、无识别内容；trace.log 显示
  模型目录选定: ...\models\ocr 后紧跟
  引擎加载失败: No such file or directory: ...\rapidocr_onnxruntime\config.yaml
- 根因：RapidOCR 构造时仍会读包内 
  apidocr_onnxruntime\config.yaml（参数解析），
  Nuitka 默认不打包包内数据文件 → dist 里 rapidocr 包缺 config.yaml → 引擎加载失败
  → 识别全空串 → md 只剩文件名列表
- 修复：打包命令加 --include-package-data=rapidocr_onnxruntime
- 验证：重打包后 trace.log 应出现 OCR 引擎加载成功：本地外置模型 ...\models\ocr
